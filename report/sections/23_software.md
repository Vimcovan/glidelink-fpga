## 2.3 软件系统介绍

### 2.3.1 软件整体介绍

软件分为两部分：

- 板上软件：运行在两块板的PS上（PYNQ 3.1，Ubuntu 22.04，Python 3），负责取图、送图、收图、射频控制和显示，结构见图2-20；
- PC端工具链：负责模型训练、整数量化与导出、神经网络顶层例化与参数文件生成、比特流构建和测量数据分析，结构见图2-26。

板上程序全部由systemd服务管理，上电约1分钟后链路自动建立，触摸屏显示GUI，无需连接上位机。

### 2.3.2 软件各模块介绍

#### 2.3.2.1 TX主程序`tx_camera.py`

TX主程序的流程见图2-21，它由一个主循环和若干后台线程组成：

- 主循环：取一帧新图像 → 必要时切换模式 → 送入PL → 转发预览。
- 数据源线程：三个线程分别维护摄像头、预设视频（30 fps循环播放）和预设图（按30 fps重复）的最新一帧，并带序号；主循环只取序号比上次新的一帧，同一帧不会重复送入编码器。摄像头图像经MJPG解码、中心裁剪480×480、用OpenCV的区域插值（`INTER_AREA`）缩小到256×256、BGR转RGB，得到的uint8 (H, W, C)数组正好是编码器要求的NHWC顺序；饱和度、对比度、gamma用`v4l2ctl.py`直接调用V4L2 ioctl设置。摄像头为可选外设：未连接时信源为预设视频，摄像头线程每5秒检查一次设备，运行中插上即可切换，拔下时自动回到预设视频；GUI选择的信源保存在`tx_source.txt`中，重启后沿用。
- 控制线程：接收GUI发来的切换信源、切换模式、设置TX衰减命令和对时请求，每条命令都回复当前状态。
- 预览线程：把交给编码器的那一帧原图发给GUI，用于计算PSNR；只保留最新一帧并在单独的线程中发送，主循环不等网络。

表2-13　TX主程序的关键输入输出

| 函数 | 输入 | 输出 |
|---|---|---|
| `JsccTx.send_image(img)` | (256, 256, 3) uint8 | MM2S DMA送入196,608字节；DMA受编码器反压，返回时编码器已收下整幅图 |
| `JsccTx.send_packet(pkt)` | 12,272字节SSCC包 | 同一DMA送入SSCC发射链 |
| `JsccTx.set_mode(m)` / `set_source(s)` | 工作模式（DeepJSCC-Q / SSCC）；数据源（编码器 / PRBS自测） | 写控制寄存器中的模式位或数据源位，PL在帧边界切换 |
| `JsccTx.set_tx_atten(db)` | 0\~89.75 dB | 经SPI写AD9361的TX衰减寄存器，立即生效 |
| `JpegFit.encode(img)` | RGB图像 | 不超过12,260字节的JPEG、质量因子q |

![TX 主程序流程](figures/sw/tx_flow.png)

图2-21　TX主程序流程（左）与JPEG质量自适应（右）。

- 启动自检：TX板的AD9361初始化与相位扫描在PL中自动完成，需要几秒。主程序加载比特流后先切到PRBS源，1秒内发往DAC的帧计数增加超过300帧才认为DAC侧已就绪，然后切到编码器；否则重新加载，最多5次。
- 模式切换：切换到SSCC前先等60 ms，让编码器把最后一帧（约33 ms）送完，再写控制寄存器中的SSCC模式位；PL中的`frame_src_mux`也只在帧边界切换，不会出现半帧。
- JPEG质量自适应：为了公平对比，SSCC每幅图必须和DeepJSCC-Q一样只占32,768个信道符号，即JPEG码流不能超过一个包的12,260字节。JPEG的码长随画面复杂度变化，固定质量因子要么放不下、要么浪费带宽，所以每帧选择能放进包的最大质量因子：从上一帧的q开始，放不下就以5为步长下调；第一次就放得下且q < 95，则试一次q + 5。

#### 2.3.2.2 RX服务`rx_server.py`

RX服务由7个线程组成，共用一个锁保护MMIO写入和DMA（表2-14）。

表2-14　RX服务的线程

| 线程 | 周期 | 输入 | 输出 |
|---|---|---|---|
| 图像接收 | 每帧 | 图像DMA（S2MM），两个缓冲交替；图像转发设为连续模式 | 一帧196,608字节放入发送队列 |
| 图像发送 | 每帧 | 发送队列 | UDP图像消息 |
| 遥测 | 10 Hz | 遥测快照（4级 × 20个符号 × 64）、寄存器计数 | 遥测消息：状态 + 星座数组 |
| 频谱 | 2 Hz | 下一帧开始时触发抓取9,728个ADC采样 | 帧内与帧前噪声的Welch功率谱（256点，Hann窗，50 %重叠） |
| SSCC包转发 | 250 Hz轮询 | 遥测接口中的SSCC包序号与双缓冲 | SSCC包消息：12,272字节 |
| AGC记录 | 2 Hz | PHY同步帧计数、增益 | 失步 / 恢复时记录AGC寄存器快照（只读） |
| AGC看门狗 | 2 Hz | PHY同步帧计数、增益 | 必要时复位AGC（2.3.2.3节） |

PS接收图像的速度即使跟不上，丢帧也只发生在PL的URAM帧缓存（整帧丢弃），PHY不会被反压。DMA等待超时后，用AXI DMA的软复位（S2MM控制寄存器bit 2）清除挂起的传输，再重新启动通道。

#### 2.3.2.3 AD9361的PS初始化与AGC看门狗`ad9361_ps.py`

PS初始化（`AD9361.init`，图2-22左）：ADI配置工具生成的初始化序列由`lut_to_json.py`转换成JSON操作列表，操作有四种：`w`（写寄存器）、`r`（读寄存器）、`delay`（延时）和`poll`（轮询某寄存器的若干位直到等于期望值，超时报错并指出是哪一步）。执行顺序为：射频控制寄存器写001（切到PS控制，AD9361复位引脚RESETB拉低）→ 2 ms后写011（释放复位）→ 逐条执行操作 → 写111（初始化完成，PL释放AD9361一侧的FIFO，并把收发控制引脚ENABLE / TXNRX拉高）。RX的初始化放在PS，AGC等射频参数修改后可以直接上板验证，不需要重新综合。

AGC看门狗（`AgcGuard.check`，图2-22右）：AD9361的快速AGC（fast attack）[10]是为突发通信设计的：在一个包的前导期间快速调整增益并锁定，锁定后只在检测到过载、更强信号等事件时才调整；信号持续变弱时，它不会主动升高增益，而是由基带在包与包之间重新启动AGC。本作品由PS在链路失步时重启：

- 每0.5 s读PL的PHY同步帧计数和当前增益索引（普通的寄存器读，不经过SPI），计算最近0.5 s的同步帧率；
- 同步率低于5帧/s、增益索引小于增益表上限，且距上次复位已超过3 s时，经SPI复位AGC状态机（AD9361的0x0FA寄存器即AGC配置1（增益控制模式），先写0x05再写0xE5）。

判据只用同步率和增益是否到顶两个量，与环境的底噪、接收功率无关；TX正常发送时同步率约30帧/s，看门狗不动作。

#### 2.3.2.5 手机控制页`web_server.py`

测试远距离传输时，两板间不方便连网线，因此RX板上另运行一个网页服务（tornado，端口8080），用手机浏览器即可查看两路实时画面和物理层指标，并控制链路（图2-24）。两块板和手机连接同一个手机热点（板载Microchip WILC模块，2.4 GHz）：

- 画面：每块板把自己的画面直接发给手机，不经另一块板转发。TX主程序在8081端口提供交给编码器的原图，RX服务把解码图编码为JPEG推送给网页服务，两路都以MJPEG流（`multipart/x-mixed-replace`）发送，由浏览器的`<img>`直接显示。
- 地址：热点分配的地址不固定。GUI的手机页读取RX板WiFi网口的地址，显示控制页地址和二维码，手机扫码进入；网页服务在WiFi子网内广播状态查询，由TX的应答得到TX板地址，页面再从该地址取TX原图。
- 状态与控制：页面经WebSocket每秒接收4次状态，星座、逐子载波SNR和频谱只在物理层页打开时发送。衰减、模式和信源命令以UDP直接发给TX板；两板连着网线时改由GUI转发，触摸屏与手机上的控件保持一致。PSNR与端到端时延需要把原图和重建图放在一处比较，只在两板连网线时由GUI给出，未连线时手机上显示“–”。

WILC模块的上行吞吐只有约2.5 Mbit/s，一路30 fps的JPEG流就要占满。若每帧都写入TCP连接，来不及发送的数据会在内核缓冲区中排队，画面滞后可达数秒，并随拥塞控制时快时慢。因此每路MJPEG限为15 fps、JPEG质量65（每帧约8 KB，约1 Mbit/s）；每帧写入前读取套接字中尚未发出的字节数（`SIOCOUTQNSD`），超过16 KB时跳过该帧，始终只发最新的一帧；连续5 s无法发送则关闭连接。经手机热点实测，一路画面稳定在约14 fps。WILC的省电模式会使往返时延升至约170 ms，开机时将其关闭。

#### 2.3.2.6 Mali-400 GPU离屏三维渲染`h3d_render.py`

信道 |H| 三维曲面（52个子载波 × 最近5秒）是物理层页上最直观的一张图，由ZU5EG片上的Mali-400 MP2 GPU（1个几何处理器、2个像素处理器，500 MHz）渲染。

驱动：PYNQ-ZU镜像的内核（6.6.10-xilinx-v2024.1）没有打开开源Mali驱动lima（`CONFIG_DRM_LIMA`）及其依赖`DRM_SCHED`、`DRM_GEM_SHMEM_HELPER`，而设备树中已有符合lima要求的GPU节点（`gpu@fd4b0000`），用户态Mesa 22也带有`lima_dri.so`。因此取Xilinx linux-xlnx对应标签的`drivers/gpu/drm/{lima,scheduler}`与`drm_gem_shmem_helper.c`，在板上以外部内核模块方式编译（`src/sw/board_setup/gpu_lima/`），开机自动加载。板上内核由gcc 12编译而板上只有gcc 11，所以在一份私有的内核构建树中单独生成arm64头文件和`modpost`（不经过会重跑kconfig的顶层Makefile），并用一个编译器包装脚本去掉gcc 11不支持的编译选项。

渲染方式：板上X服务的显示驱动（armsoc）不支持GPU加速，经X的OpenGL程序只能得到软件渲染。因此三维曲面由一个独立的渲染进程绕过X、直接在lima的render节点上离屏绘制，再把像素读回交给GUI当作图片显示，界面其余部分仍由X显示（图2-25）：

1. 初始化GPU：按驱动名在`/sys/class/drm/renderD*`中找到lima的render节点，经`libgbm`创建GBM设备，用`eglGetPlatformDisplay(EGL_PLATFORM_GBM_KHR)`初始化EGL，建立OpenGL ES 2.0的无表面上下文；渲染目标是一个帧缓冲对象，RGBA纹理作颜色附件，16位深度渲染缓冲作深度附件。
2. 生成几何（NumPy，约7 ms）：T×N的 |H| 历史（N = 52，T为最近5 s的快照）构成三角网格；法向量由有限差分得到，按Lambert模型着色，颜色按 |H| 在三段色图中插值；另有曲面网格线、地面网格和坐标轴的线段。
3. 绘制：一个只做MVP变换的顶点着色器加一个直通片元着色器；先画曲面（开启多边形偏移，使网格线浮在曲面上），再画线段；相机参数与PC版pyqtgraph的视角一致。
4. 读回：`glReadPixels`读回RGBA图像，约45 ms；投影矩阵预先在y方向翻转，读回的数据已是“首行在上”，不需要再翻转。
5. 与GUI通信：GUI中的一个工作线程经标准输入、输出与渲染进程交换数据，请求包含图像尺寸和 |H| 数组，响应包含渲染耗时和像素；同一时刻最多一个请求在途，新数据直接覆盖未发出的旧请求。坐标轴的刻度文字由Qt绘制，用同一个`camera()`和`project()`函数把三维坐标投影到像素，与GPU画出的坐标轴对齐。

没有lima驱动时，GUI自动改用二维瀑布图。每帧渲染加读回约60 ms，曲面每秒刷新2.5次，渲染进程约占一个CPU核的10 %，`rx_server.py`保持每秒接收30帧。

#### 2.3.2.7 PC端工具链

PC端工具链从训练一直延伸到上板测量（图2-26），各环节之间都以文件交接。

![PC 端工具链](figures/sw/pc_toolchain.png)

图2-26　PC端工具链：模型训练 → 整数量化 → RTL例化 → 比特流 → 测量。

模型与训练（`src/model/`）：

- 模型配置：编码器按DeepJSCC-Q期刊版本[2]实现，主通道数C = 32，潜变量通道数16，总下采样倍率4。256×256 RGB图像编码为64×64×16的潜变量，相邻通道配为I/Q，每帧32,768个64QAM符号，带宽比为每像素0.5个复符号。解码器为浅层结构（2.2.3.1节）。
- 训练目标：在10 dB AWGN信道下训练，损失为重构均方误差加权重0.05的星座分布KL正则，

  $$\mathcal L=\mathrm{MSE}(\mathbf x,\hat{\mathbf x})+0.05\,D_{\mathrm{KL}}(p\,\|\,u)$$

  其中p为批次内软分配的平均星座概率，u为均匀分布。

- 量化方式：前向用最近星座点的硬量化，反向通过距离softmax的软量化传递梯度（`hard + soft - soft.detach()`）。训练前向与部署时的符号集合一致，编码器又能得到可用的梯度；KL项防止符号使用概率过度集中。
- 训练数据：DIV2K[13] train 800张 + Flickr2K[14] 2650张；优化器Adam，有效批量16。
- 训练过程分两段。第一段按论文结构训练完整的编码器与对称解码器（学习率2×10⁻⁴，1200轮），得到编码器。第二段训练浅层解码器（`train_shallow_dec.py`）：先冻结编码器、以无噪声输入训练解码器300轮；再在10 dB AWGN下联合训练编码器与解码器（解码器学习率3×10⁻⁴、编码器1×10⁻⁴，验证集PSNR 30轮不提高时减半，KL权重不变）共1400轮；最后200轮做8位权重的量化感知训练：前向时卷积权重按部署规则逐输出通道量化为8位，梯度加到浮点权重上。部署检查点为量化感知训练的第172轮（3.2.3节）。

整数量化与导出：`quant_shallow.py`与`export_shallow.py`对检查点做W8A12量化，卷积权重为逐输出通道缩放的8位整数，激活为逐张量缩放的12位整数，PWL输入的定标取2的幂次；编码器沿用`int_ref.py`的整数算法，它规定偏置、舍入、饱和与非线性的整数运算，是RTL的逐比特参考。导出的`manifest.json`包含神经网络结构、张量形状、量化参数和存储规划，`gen_rtl_top.py`据此例化手写的RTL模块、填写参数并完成顶层连线，`gen_rtl_init.py`把权重与重定标参数写成ROM初始化文件（2.2.3.1节）。量化损失在两个数据集上都不超过0.03 dB（表2-15）。

|---|---:|---:|---:|

构建与测量：`build/build_hw.tcl`按`src/hw/<tx|rx>/files.txt`新建工程、加入IP、生成PS块设计，用Vivado 2025.2默认策略完成综合、实现和比特流生成。`board/tests/`中的测量脚本完成链路扫描（`measure_link.py`）、数据辅助SNR计算（`analyze_const.py`）和基于PL帧计数器的分段时延测量（`pl_events.py`、`seg_latency.py`），结果见第三部分。
